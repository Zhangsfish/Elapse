### PASS — App Group privacy boundary and final signing

The shared group `group.com.zhangsfish.elapse` is declared only by the main App and Monitor extension. The Report extension does not receive the App Group.

The shared store contains only app-owned experiment / diagnostic metadata:

- experiment UUID and generation;
- phase;
- selected-application **count**;
- callback/request timestamps and safe status/error codes;
- stale/duplicate counters;
- receipt keys derived from experiment ID + threshold event.

It does not persist FamilyControls tokens, selected App identities, bundle IDs, DeviceActivityReport output, or protected Screen Time usage data.

### PASS — experiment identity prevents old receipts from suppressing same-day restart

Each Start creates a new UUID. The DeviceActivity activity name carries that UUID.

Receipt identity is `experimentID|eventName`, not calendar date + event.

A new experiment clears current receipt state and uses a distinct identity, so a prior five-minute receipt cannot suppress the same five-minute threshold in a later same-day experiment.

Unit tests cover distinct experiment identity and same-day receipt independence.

Device evidence separately confirms a second same-day experiment (`722d1c70`) received its own current-experiment five-minute callback, accepted notification request, and visible pulse.

### PASS — stale/duplicate callbacks fail closed

The Monitor extension extracts the experiment UUID from the callback activity name.

A callback is request-eligible only when:

- the activity name contains a valid experiment UUID;
- that UUID equals the shared store's current experiment ID;
- the current experiment phase is still `registered`;
- the threshold event is valid;
- the experiment-scoped receipt has not already been recorded.

Otherwise it is classified stale, duplicate, or invalid and no notification is requested.

The asynchronous notification-request completion performs the current-experiment check again before mutating request diagnostics. A late completion from an old experiment therefore cannot overwrite the new experiment's status.

No stale callback actually occurred during the owner test. This part of the gate is accepted from SOURCE + UNIT_TEST evidence, not DEVICE_OBSERVED evidence.

### PASS — selection and monitoring configuration cannot silently diverge

While an experiment is starting/registered, selection editing is disabled and `updateSelection` also rejects changes programmatically through the view binding path.

After Stop, the experiment phase becomes stopped and selection becomes editable again.

Owner observation matches this behavior: selection was unavailable during monitoring and available after Stop.

### PASS — first real shared-pool threshold

For experiment `5c520eb7`, the owner recorded:

- about one minute in an unselected App with no pulse;
- selected App A for 2m18s;
- selected App B for 1m44s;
- selected subtotal 4m02s, still without the five-minute pulse;
- about one more minute in selected App A;
- then a visible five-minute pulse.

The app-owned diagnostic showed a current-experiment five-minute callback and accepted notification request.

This supports shared-pool accumulation across two selected Apps and does not support treating the unselected-App minute as selected usage. The owner timings are approximate wall-clock observations, not authoritative Screen Time measurements; this audit does not claim second-level precision.

### PASS — truthful time scope

Threshold events still use `includesPastActivity=false`.

The notification copy now states that the selected Apps reached the named threshold **since this monitoring experiment began**. It no longer presents the experiment-start cumulative threshold as a natural-day Today total.
