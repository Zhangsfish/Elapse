### PASS — product interval model is separated from S00 fixtures

`DayPulsePlan` is distinct from historical S00 six-threshold constants.

Supported values are 5/10/15/30/60 minutes, default 5.

The selected interval is persisted locally and cannot be changed while monitoring is active.

### PASS — day-range candidate ladders are deterministic and bounded

The 25-hour-exclusive planning ceiling yields:

- 5m: 299 events, max threshold 1495m;
- 10m: 149 / 1490m;
- 15m: 99 / 1485m;
- 30m: 49 / 1470m;
- 60m: 24 / 1440m.

This is explicitly a planning ceiling, not an assertion that every local day has 25 hours or that DST/midnight lifecycle is complete.

Event-name parsing is canonical and bounded. A callback is additionally required to belong to the current configured interval plan; for example, a 10-minute callback under a 15-minute configuration is invalid and cannot request a pulse.

### PASS — new configuration identity scopes receipts and callbacks

Each Start creates a new UUID-backed configuration.

A new interval/configuration clears current receipts and diagnostics. Old activity callbacks and late notification completions remain fail-closed against the current configuration identity.

Tests cover high thresholds including 720 and 1495 minutes, a 15-minute replacement config, invalid off-plan thresholds, old callbacks and old completions.

### PASS — registration count is verified against DeviceActivity itself

After `startMonitoring`, the App verifies:

- the activity is present in `DeviceActivityCenter.activities`;
- `DeviceActivityCenter.events(for: activity).count` equals the planned event count.

Mismatch immediately stops the activity and records a safe registration failure instead of claiming success.

On app refresh/relaunch, the same system registration is queried again; the displayed registered count is not merely a cached planned count.

### PASS — target iPhone accepts the large event ladders

On Everwhile 44.1:

- default 5-minute config: 299 planned / **299 system-registered**, no registration error;
- 15-minute config: 99 planned / **99 system-registered**, distinct configuration ID, no registration error.

This directly closes the S01-A unknown about per-activity event-dictionary feasibility on the target device.

It does **not** prove every threshold will fire correctly all day.

### PASS — scalable diagnostics

The UI no longer renders hundreds of event rows.

It exposes interval, configuration ID, planned/registered counts, aggregate callback/request counters, most recent accepted threshold, plan-only next threshold, and only a bounded recent threshold list.

No selected tokens, App identities, Today/report data or exact sessions are added to the shared diagnostic store.

## Non-blocking notes

1. Reopen persistence and final stopped/restored-5 state are OWNER_REPORT rather than separate final screenshots.
2. Pulse callback/notification delivery was intentionally not retested; S00 already established that chain. Registration success does not prove all-day reliability.
3. The 25-hour ladder is a planning ceiling; automatic midnight rollover, timezone/DST and lifecycle recovery are not yet implemented.
4. PR #18 body still contains an older DEVICE_NOT_RUN statement; authoritative S01-A reports supersede it.
5. Current iOS 26 developer reports describe premature DeviceActivity threshold callbacks. This is not an API contract, but later lifecycle work should fail closed against physically impossible early callbacks rather than blindly trusting every callback.
